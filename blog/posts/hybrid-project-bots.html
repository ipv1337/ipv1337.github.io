Hybrid Project-Scoped AI Bots with OpenClaw

Stop re-explaining your codebase every time. Here's how I layered project-scoped bots on top of my virtual engineering org — each one pre-loaded with cluster configs, file paths, and pending work, yet still able to delegate to role specialists when needed.

The Problem: Role Bots Have No Memory

If you've followed the Virtual Engineering Org series, you know the setup: five persistent bots running on OpenClaw, each with its own Telegram handle and specialist focus. The Lead orchestrates. The Architect reviews. The Writer drafts. The Analyst researches. The DevOps bot validates. It works.

But there's a friction point that only shows up after you've been using the system for a few weeks. Every time you open a project-specific conversation — say, asking the Architect to review your GKE deployment config — you spend the first few messages re-establishing context. Which cluster. Which namespace. Which values file. What state the PoC is in. What's already been tried. The Architect is brilliant; it just has no idea who you are or what you're working on.

Role-based bots are specialists without projects. They know how to do things. They don't know what you're building.

The fix is obvious once you see it: give each active project its own bot, pre-loaded with everything it needs to know. Keep the role specialists for deep work. Let the project bot know when to hand off.

Three Options, One Winner

Before building, I sketched out three architectural options. The trade-offs are worth understanding because the answer isn't obvious — each model has real advantages.

Role-based only Project-based only Hybrid ✓
Context None — re-explain every time Full project context baked in Project bots have context; role bots for specialization
History All projects mix in one thread Scoped per project Best of both
Bot count Low (5) Scales with every project Moderate — only active projects get a bot
Capability Deep specialist knowledge Full-stack per bot, but shallow Deep capability via delegation

A pure project-based model sounds appealing until you think about what "full-stack per bot" actually means: you're duplicating system design expertise, writing expertise, and research expertise across every project bot. That's a lot of prompt surface area to maintain, and none of it is as deep as a dedicated specialist.

The hybrid wins because it separates two different kinds of knowledge: project context (what we're building, current state, useful commands) and role capability (how to design systems, write clearly, audit deployments). Project bots hold the former. Role bots hold the latter. Delegation bridges them.

How It's Wired Up

The implementation is three parts: a Telegram bot account, a binding that connects the account to an agent, and a workspace directory that holds the project's context. Let's walk through each.

1. Account Configuration

Each project bot gets a dedicated Telegram bot (created via BotFather) registered as an account in openclaw.json. The key settings are dmPolicy: allowlist and allowFrom locked to your own Telegram ID — these bots are personal, not public: 

// openclaw.json — accounts section
"accounts": {
  "proj-kubeshark": {
    "botToken": "YOUR_BOT_TOKEN",
    "dmPolicy": "allowlist",
    "allowFrom": ["YOUR_TELEGRAM_ID"],
    "groupPolicy": "disabled",
    "streaming": "partial"
  },
  "proj-ipv1337": {
    "botToken": "YOUR_BOT_TOKEN",
    "dmPolicy": "allowlist",
    "allowFrom": ["YOUR_TELEGRAM_ID"],
    "groupPolicy": "disabled",
    "streaming": "partial"
  }
}

2. Binding Agent to Account

A binding tells OpenClaw: when a message arrives on this account via this channel, route it to this agent. Without a binding, all Telegram traffic routes to the default agent: 

// openclaw.json — bindings section
"bindings": [
  {
    "agentId": "proj-kubeshark",
    "match": {
      "channel": "telegram",
      "accountId": "proj-kubeshark"
    }
  },
  {
    "agentId": "proj-ipv1337",
    "match": {
      "channel": "telegram",
      "accountId": "proj-ipv1337"
    }
  }
]

3. Agent Definition with Scoped Workspace

The agent definition points to a dedicated workspace directory. OpenClaw loads every file from this directory automatically on every session start — that's where the project context lives: 

// openclaw.json — agents section
{
  "id": "proj-kubeshark",
  "workspace": "/Users/james/.openclaw/workspace-proj-kubeshark",
  "identity": {
    "name": "Shark",
    "theme": "Platform Engineer — GKE/eBPF specialist",
    "emoji": "🔬"
  }
}

The Workspace: Seven Files That Replace Your Context Dump

Every project workspace follows the same structure. These seven files are what the agent loads on startup instead of you typing "okay so we're working on a GKE cluster, the namespace is qa-stockkeeper, the values file is at..." 

workspace-proj-kubeshark/
├── IDENTITY.md   # Persona: name, emoji, vibe, role
├── USER.md       # Owner profile — who James is, preferences
├── MEMORY.md     # Full project context (cluster, commands, status)
├── SOUL.md       # Orchestrator-first behavior guidelines
├── AGENTS.md     # Delegation rules + spawn examples
├── HEARTBEAT.md  # Periodic checklist (health checks, reminders)
└── TOOLS.md      # Tool notes and local conventions

The heavy lifting happens in MEMORY.md. This is where I document everything the bot needs to hit the ground running — cluster name, namespace, key file paths, current PoC status, known issues, and the commands I run most often: 

# MEMORY.md — Kubeshark PoC

## Project Status
Active PoC. Kubeshark deployed to `qa-stockkeeper` namespace.
Goal: validate eBPF-based packet capture for service mesh traffic analysis.

## Key Details
- Cluster: gke_prj-rx-int-ooms-a557_europe-west3_ooms-rx-int-euw3-3
- Target namespace: qa-stockkeeper
- Values file: ooms-shared/kubeshark/values.yaml
- Kubeshark UI: port-forward 8899 → kubeshark-front:80

## Useful Commands
kubectl get pods -n kubeshark
kubectl port-forward -n kubeshark svc/kubeshark-front 8899:80
helm upgrade --install kubeshark kubeshark/kubeshark \
  -f ooms-shared/kubeshark/values.yaml -n kubeshark

## Pending Work
- [ ] Validate packet capture coverage for gRPC traffic
- [ ] Export traffic reports to GCS bucket
- [ ] Write PoC summary doc for platform review

And AGENTS.md is what makes the hybrid model work. It defines exactly when the project bot should handle something itself versus when it should spin up a role specialist: 

# AGENTS.md — Kubeshark Bot Delegation Rules

You are Shark, a project-scoped bot for the FLYR Kubeshark PoC.
Handle day-to-day project ops yourself. Delegate deep work to specialists.

## When to Delegate

| Agent         | ID          | Delegate When                              |
|---------------|-------------|--------------------------------------------|
| 🏗️ Architect  | architect   | System design, ADRs, trade-off analysis    |
| ✍️ Writer     | writer      | PoC docs, READMEs, blog posts              |
| 🔍 Analyst    | analyst     | Research, options comparison, benchmarking |
| 🔧 DevOps     | devops      | QA, validation, deployment readiness       |

## Handle Yourself
- kubectl commands, pod status checks
- Port-forward setup, log tailing
- Values file edits and quick config questions
- Status updates and progress tracking

What This Looks Like in Practice

Here's a concrete example. Before the hybrid setup, asking about the Kubeshark deployment went like this:

Me → Architect bot: "Can you check the Kubeshark values file and tell me if the node affinity settings look right for our cluster?"

Architect: "Sure, what's the cluster name and where's the values file?"

Me: "It's gke_prj-rx-int-ooms-a557_europe-west3..."

After the hybrid setup, the same question goes to Shark:

Me → Shark: "Check the values file — does the node affinity look right?"

Shark: Reads ooms-shared/kubeshark/values.yaml, checks the cluster context it already knows, and either answers directly or says "this needs architectural review — spawning the Architect."

No re-explanation. No lost context. The project bot starts from the right place, handles what it can, and calls in a specialist when the question genuinely warrants it.

The delegation trigger in AGENTS.md also means the project bot doesn't try to do everything itself. If I ask Shark to write a PoC summary document, it knows that's a Writer task — it'll spawn the Writer sub-agent with the right context pre-populated from MEMORY.md. The Writer gets a detailed brief without me having to write it.

Three Things I Got Wrong First

The architecture looks clean in hindsight. Getting there involved a few wrong turns worth documenting.

1. MEMORY.md needs structure, not prose

My first MEMORY.md files were narrative paragraphs describing the project. They read well but didn't work — the bot couldn't quickly extract the cluster name or the right kubectl command from a paragraph of context. Switching to structured markdown with explicit headers (## Key Details, ## Useful Commands, ## Pending Work) made the bot dramatically more useful. LLMs scan structured data; they stumble through embedded facts in prose.

2. Don't give project bots full role capability

My first instinct was to make each project bot as capable as possible — load it up with architectural knowledge, writing guidelines, research methodology. This backfired. The bot tried to handle everything itself instead of delegating, and the quality of deep work suffered. The right design is a clean handoff: project bots are excellent at project ops, not specialist craft. Keep SOUL.md focused on "orchestrate, don't do."

3. Bot count creep is real

Every interesting side project wants its own bot. Resist. Four project bots is about the sustainable limit for a solo developer. Each one needs its MEMORY.md kept up to date — that's real maintenance overhead. Only active projects with multiple weekly interactions justify a dedicated bot. Low-frequency projects are better served by the role-based bots with a quick context paste.

When to Add a Project Bot

Not every project needs this. Here's the rough heuristic I use:

✅
Add a project bot when:
  • You're touching the project multiple times per week
  • The project has meaningful state (cluster configs, API keys, file paths, current status)
  • You find yourself re-explaining the same context more than twice
  • The project spans multiple roles (needs both architecture and writing, both research and DevOps)
⚠️
Skip the project bot when:
  • The project is a one-off task or PoC you'll abandon in a week
  • The project only needs one type of specialist (just use the role bot directly)
  • You can't commit to keeping MEMORY.md up to date

The Full Architecture

Nine bots total: five role specialists and four project bots. All running on the same OpenClaw gateway, sharing the same tool surface, but each with a distinct identity and scope: 

OpenClaw Gateway
│
├── Role Bots (persistent specialists, no project context)
│   ├── 🤖 Lead (Pi)         — orchestration, system ops, routing
│   ├── 🏗️ Architect         — system design, ADRs, technical review
│   ├── ✍️ Writer            — prose, docs, blog posts
│   ├── 🔍 Analyst           — research, options comparison
│   └── 🔧 DevOps            — QA, validation, infra checks
│
└── Project Bots (context-rich, orchestrator-first)
    ├── 🔬 Shark (proj-kubeshark)  — GKE/eBPF network capture PoC
    ├── 🌐 Pixel (proj-ipv1337)   — portfolio site & blog pipeline
    ├── 📱 Droid (proj-android)    — OpenClaw Android companion app
    └── 🏠 Casa  (proj-casa)       — Google Home / GCP integration

From your phone it looks like nine separate Telegram contacts. Under the hood it's one OpenClaw gateway managing nine isolated agent contexts — each loading the right workspace on startup.

When Shark needs architectural input, it spawns the Architect sub-agent with full MEMORY.md context pre-populated in the task brief. When Pixel needs a new blog post written, it delegates to the Writer. The project bots are the entry point; the role bots provide the depth.

The Takeaway

Role-based bots give you specialist depth. Project-scoped bots give you continuity. The hybrid gives you both — but only if you keep the responsibilities clean.

Project bots should be narrow and context-rich. They know your codebase, your cluster, your current status. They handle project ops themselves and delegate everything that needs specialist depth. SOUL.md says "orchestrate, don't do" — and they mean it.

The real payoff is the compounding effect. As MEMORY.md grows richer — capturing decisions made, issues resolved, commands proven to work — the project bot gets genuinely better at the project. Not because the model changed, but because the context did. That's institutional memory you built, not hallucinated.

Setup takes about 20 minutes per project bot: create a Telegram bot via BotFather, add the account and binding to openclaw.json, create the workspace directory, seed the seven context files. The MEMORY.md will take another 30 minutes to write properly — that's the investment that pays off every day after.

💡
Start small: Pick your one most active project and build a single project bot. Live with it for a week. You'll know within two days whether the MEMORY.md was good enough — if you're still answering "what cluster?" questions, it wasn't. Iterate on context before adding more bots.
