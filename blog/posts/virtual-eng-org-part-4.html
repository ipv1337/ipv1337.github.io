Making It Stick — Teaching Your AI Workflow to Self-Organize

Adding delegation rules, routing frameworks, and an orchestrator mindset to a virtual engineering org. How three files made the difference between a team that sits idle and one that routes itself.

Somewhere between Part 3 and this post, I caught myself doing something embarrassing: I'd written a research request, a blog outline, and half a technical review — all inline, in a single chat thread — while four perfectly capable sub-agents sat idle.

I'd built a team. I just wasn't using it.

The agents existed. The workspaces were set up. The orchestration skill had been shipped in Part 3. But Pi — the lead agent — kept defaulting to doing everything himself. Research, writing, validation: all jammed into one sprawling context window that grew slower and worse as it got longer.

The fix wasn't a smarter model. It wasn't a better prompt. It was organizational design — the same thing that turns a group of individual contributors into a functioning team. You have to write the rules down. You have to make delegation explicit. And you have to give your AI lead an identity that sees itself as an orchestrator first, not a doer.

This post is about the three files that made that shift happen — and an honest account of what "the first autonomous pipeline run" actually looked like.

What "Self-Organizing" Actually Means

Let's clear something up before we go further: this is not ML self-organization. The model is not discovering structure from data or adapting its own weights. When I say "self-organizing," I mean something far more mundane — and far more controllable.

The org chart lives in files. AGENTS.md defines the roster, the delegation triggers, and the pipeline steps. SOUL.md shapes the lead agent's identity. These files are loaded into the model's context at the start of every session. The model reads them and follows them — or doesn't, if the language is soft enough to ignore.

That distinction matters. The agents existed since Part 2. The Architect, the Writer, the Analyst, the DevOps specialist — they all had identities, workspaces, and defined strengths. What they lacked was a routing layer: explicit, mandatory rules telling the lead agent when to delegate and to whom.

Without that layer, the lead agent's default behavior is to handle everything. It's not lazy or stubborn. It's just doing what language models do: generating the next token in the most natural continuation of the context. And the most natural continuation of "write me a blog post" is… to write the blog post.

💡 Key Insight
Your AI doesn't self-organize. You write the org chart, and it follows it. That's not a limitation — it's a feature. You get deterministic, auditable routing instead of emergent behavior you can't predict or debug.

The Before State

Here's what the pipeline looked like in practice before Part 4, even with the orchestration skill in place from Part 3:

James: "Write a blog post about X."
Pi: starts writing the blog post.

No research phase. No outline. No Architect review. No Writer sub-agent. Just Pi, inline, generating 1,200 words with increasing context bloat and a quality curve that bent downward as the session got longer.

The AGENTS.md roster was there. The sub-agents could be spawned. But the skill instructions used language like "consider delegating" and "you may want to use the Analyst for research." Soft suggestions. And soft suggestions, in my experience, are suggestions that never get taken.

The orchestration skill from Part 3 defined the pipeline steps, but it was a reference document more than a decision engine. Pi would read it when explicitly told to run the blog pipeline. He wouldn't read it unprompted just because a blog post was requested.

⚠️ Gotcha
If you build agents without giving the lead explicit rules about when to use them, it defaults to doing everything itself. Every time. "Consider delegating" is not a delegation policy. It's a polite suggestion that gets ignored the moment the model starts generating.

The deeper problem was identity. Pi thought of himself as a capable generalist assistant — someone who could write, research, validate, and ship. That's a reasonable default for a solo assistant. It's the wrong identity for a team lead.

I'd built a team of four and was still doing all the work myself. The agents weren't the bottleneck. The org chart was.

Three Files, One Rule

The changes were surgical. Three files, each doing a different job. The underlying rule they all enforce: delegation is mandatory, not optional.

AGENTS.md — The Delegation Rules

The biggest change to AGENTS.md was replacing vague guidance with a mandatory routing table. The key section now reads:

📋 AGENTS.md — Delegation Triggers (MANDATORY) 
### Delegation Triggers (MANDATORY)

**Always delegate when the request matches:**

- **Architecture / Design**: technical deep-dives, trade-offs, ADRs → 🏗️ Architect
- **Writing / Content**: blog posts, docs, technical articles → ✍️ Writer (+ 🏗️ Architect review)
- **Research / Analysis**: research X, compare A vs B, market surveys → 🔍 Analyst
- **QA / Validation**: check links, validate HTML, review build → 🔧 DevOps
- **Blog post pipeline**: Always run full pipeline:
  Analyst → Architect → Writer → Architect review → DevOps validation → Lead publishes

Notice the word "Always." Not "consider." Not "you may want to." Always.

💡 Key Insight
The word "always" does a lot of work in a system prompt. Language models are very good at following explicit imperatives and very bad at consistently following soft suggestions. If you want a behavior to be reliable, make it mandatory in the text.

The Orchestrate Skill — The Decision Framework

The orchestrate skill is a request routing decision framework added as part of this Part 4 work. When Pi reads it, he has a clear decision tree:

  • Is this architecture or design? → Architect
  • Is this writing or content? → Writer (with Architect review)
  • Is this research or analysis? → Analyst
  • Is this QA or validation? → DevOps
  • Is this a blog post? → Full pipeline, in sequence

The skill also defines what each sub-agent needs in its task description when spawned — full context, no assumptions, since sub-agents run in isolated sessions with no access to the main session's history.

SOUL.md — The Mindset Shift

SOUL.md shapes identity and tone. One line was added:

"You are an orchestrator first. When a task matches a sub-agent's specialty, delegate — don't do it yourself. Trust your team."

That's it. One sentence. But it reframes Pi's self-concept. He's not a generalist who occasionally delegates. He's an orchestrator whose job is routing and coordination, with delegation as the primary behavior rather than the fallback.

AGENTS.md gives the rules. SOUL.md shapes the identity. You need both. Rules without identity get followed mechanically and abandoned when they're inconvenient. Identity without rules is aspirational but not actionable. Together, they produce consistent behavior.

What Actually Happened

Let me be honest about the first pipeline run, because the honest version is more interesting than the polished version.

James asked for a Part 4 blog post. Pi read AGENTS.md, identified it as a blog post pipeline trigger, and — without being told to run the pipeline — spawned the Analyst sub-agent to produce a research brief and content outline. That part worked exactly as designed.

The Analyst returned a solid outline. Pi then spawned the Architect to review it for technical accuracy. The Architect added real value: flagged where the "first autonomous pipeline run" framing needed to be walked back, caught the agentId policy issue as worth sharing, and tightened the section structure. Then Pi spawned the Writer — producing the draft you're reading now.

But two real gotchas hit us along the way.

Gotcha 1: agentId Policy Restriction

When Pi tried to spawn sub-agents using the agentId field (e.g., agentId: "analyst"), the agents_list tool only returned main. Named agent IDs weren't exposed through the API — a policy allowlist that needs updating.

The workaround: sub-agents were spawned as anonymous sessions with the agent persona injected via the task description rather than the agentId field. It works, but the identity lives in the task prompt rather than being enforced at the system level.

Gotcha 2: Push-Based Auto-Announce Didn't Fire

The design intention is that when a sub-agent completes, it auto-announces back to the parent session. In this run, that didn't happen reliably. Pi had to manually check sub-agent status between steps — more "project manager checking Jira" than "fully autonomous pipeline."

🔍 Reality Check
The first pipeline run wasn't fully autonomous. Pi still needed nudging between steps. But the routing was autonomous — Pi identified the task type and delegated without being told to. That's the meaningful shift. We went from "Pi does everything" to "Pi routes correctly and coordinates the team." Full autonomy is one config fix away. That's close enough to ship.

The Architecture

Here's how the pieces fit together technically:

  James
    │
    ▼ "write a blog post about X"
  ┌─────────────────────────────────────────┐
  │  Pi (Lead Agent)                        │
  │  reads: AGENTS.md + SOUL.md             │
  │  identifies: blog post pipeline trigger │
  └─────────────────────────────────────────┘
    │
    ▼ reads orchestrate skill → decision tree
    │
    ├──► spawn Analyst   → outline + research brief
    │         └── isolated context window
    ├──► spawn Architect → technical review of outline
    ├──► spawn Writer    → full HTML draft
    ├──► spawn Architect → technical review of draft
    ├──► spawn DevOps    → HTML/link/asset validation
    │
    └──► Pi applies fixes, generates hero image
           └──► James: final approval → Pi publishes
  • Isolated context windows. Each sub-agent sees only its task description — no main session history. Focused context produces sharper output.
  • Sequential, not parallel. Agents chain one after another. Parallel spawning hits rate limits and makes debugging harder.
  • Full context in every task. Every spawn includes the full relevant context — outline, prior agent outputs, constraints. No assumptions.
📋 Minimal AGENTS.md Delegation Rules (copy-paste ready) 
## Delegation Triggers (MANDATORY)

| Request Type                          | Delegate To    |
|---------------------------------------|----------------|
| Architecture, design, trade-offs, ADRs | 🏗️ Architect  |
| Blog posts, docs, technical writing   | ✍️ Writer      |
| Research, comparison, analysis        | 🔍 Analyst     |
| QA, validation, link/HTML checks      | 🔧 DevOps      |

## Delegation Protocol
1. Identify request type → select agent from table
2. Spawn via sessions_spawn with descriptive label
3. Include FULL context in task (no assumed history)
4. Chain agents sequentially; report to user after each step

Lessons Learned

1. Explicit beats implicit

"Consider delegating" is not a policy. "Always delegate when…" is. When the rules are soft, the model's default behavior (doing the thing itself) wins. When the rules are explicit and mandatory, the routing holds.

2. Context isolation improves quality

Spawning a focused Analyst for research and a focused Architect for technical review produced better outputs than Pi doing both inline — not because the underlying model is different, but because each sub-agent has a clean, scoped context window. The Analyst isn't distracted by the writing task. The Architect isn't biased by the research.

3. Written rules need maintenance

AGENTS.md is living documentation. The routing table will drift as the team evolves. Treat it like a runbook: review it when the pipeline breaks, update it when behavior drifts.

4. Honesty about what's autonomous vs. assisted

The routing is the hard part. Getting the lead agent to correctly identify a task type and delegate without being told to — that's the meaningful capability. Full end-to-end pipeline automation is an infrastructure detail that's close but not yet shipped.

5. The routing is the hard part

Building agents is easy. Getting the lead agent to route correctly, consistently, without drifting back to doing everything himself — that's where the work is. And the answer turned out to be surprisingly simple: write it down, make it mandatory, bake it into the identity.

🔍 Reality Check
This isn't "AI that teaches itself to organize." It's AI that follows written org charts consistently. That consistency — routing the right work to the right agent, every time, without being reminded — is what was missing. Writing it down was the whole fix.

What's Next

Two concrete fixes remain before the pipeline is fully autonomous:

  1. agentId allowlist. Configure the policy so named agent IDs are exposed through the API, letting Pi target specific agent personas at the system level rather than injecting them via task description.
  2. Reliable announce. Investigate why push-based completion announcements didn't fire. Once this works reliably, Pi won't need manual polling between steps — the pipeline advances automatically.

When both are working, the flow becomes: James asks for a post, Pi identifies the trigger, five agents run in sequence, each announces completion to the next, and the finished draft lands in the publish queue. No further nudging required.

That's the target. We're close.
